# #16 컴포넌트·시스템 연결 검증과 등록 해제 대응

## 요약

대상은 [GitHub #16](https://github.com/jammer-droid/deepseek-harness/issues/16)이며 준비 상태는 `ready`다. S1–S4의 구현과 이슈 범위 수용 검증은 4/4 완료했다. 전체 저장소와 Studio 전체 회귀의 미해결 실패는 아래 검증 기록에 남기며, 전체 검증 성공이나 트래커 종료를 의미하지 않는다. 잘못된 조합의 위치별 진단과 기능 해제 후 초안 보존을 제공한다. 선행 [#15](https://github.com/jammer-droid/deepseek-harness/issues/15)는 닫혔으며 현재 기준 코드에 포함되어 있다. [설계 절차](../design-workflow.md), [제품 명세](../workflow-specification.md), [구조 검토](../workflow-architecture-review.md)를 따른다.

작업 브랜치는 `studio/feat/workflow-16`, 통합 대상은 `studio/feat/workflow`다. 시작점은 `studio/experiments`의 변경을 포함한 통합 브랜치의 설계 절차 문서 이름 변경 커밋이다. 정확한 기준 커밋은 이 문서를 처음 추가한 커밋의 부모다. 사용자가 S1–S4 전체 구현·검증·로컬 커밋을 승인했다. 푸시·통합 브랜치 병합·트래커 변경·설치 프로필 배포는 포함하지 않는다.

## 확정한 범위

- 현재 메인 역할을 유지하고 등록된 시스템의 구성과 연결을 폼으로 편집한다. 등록 정의가 허용하는 연결을 제공하고 공통 Host 검증의 위치별 진단을 표시한다. 사용자는 폼에서 잘못된 조합을 수정할 수 있어야 한다.
- 문서 형식이 유효하면 필드·참조·연결·필수 시스템 오류가 있어도 초안 저장을 허용한다. 의미 오류는 공통 Host 진단으로 반환하며 후속 적용을 막는 판정으로 사용한다. 형식 오류·리비전 충돌·저장 장애의 기존 거절과 저장 불명 상태 처리는 유지한다.
- 검증 성공은「구성 검증 통과 — 실행 지원 미확인」을 뜻한다. 공통 Host가 등록·필수 시스템·참조·연결·범위를 판정하며 실제 모델·권한·프리셋 적용 가능성을 보장하지 않는다. 후속 적용 adapter는 같은 구성 검증을 재실행하고 실제 지원 여부를 추가 확인한다.
- 연결은 등록된 입력·출력 포트 사이의 구성상 연결이다. Host는 방향·의미 식별자·허용 대상·필수 연결 수를 검사한다. 범용 데이터 전달·실행 순서 엔진은 만들지 않으며 실제 실행 의미는 기능 구현과 후속 적용 작업의 책임이다.
- 제품 UI에는 실제 등록된 기능만 노출한다. 연결 제공자가 없으면 이유를 포함한 빈 상태를 표시한다. 연결의 양성·음성·효과 해제·재등록은 실제 Loader와 격리 브라우저에 로드한 테스트 전용 제공자로 검증하며 이를 실제 연결 기능의 실행 증거로 표시하지 않는다.
- 등록 해제·버전 불일치 항목은 설정을 보존한 읽기 전용으로 표시하고 명시적인 삭제만 허용한다. 일치하는 등록이 없으면 항목의 식별 정보와 가용성 안내를 표시하고, 보존한 설정 필드는 임의로 해석하지 않으며 동일 버전이 돌아올 때 다시 표시한다. 자동 삭제·버전 변환·원시 JSON 편집을 제공하지 않는다. 연결도 누락 진단과 함께 보존하며 동일 버전 재등록 시 미저장 입력을 포함한 기존 값을 다시 해석한다.
- 임의 역할 편집은 후속 #17, 그래프 캔버스는 이번 범위 밖이다. 실제 프리셋 적용·활성화·실행을 이번 작업으로 구현하지 않는다.
- 새 실행 엔진, 범용 ECS, 재시작 후 과거 코드 복원은 범위 밖이다. 기존 General·고정 역할·experiments 기능과 공존한다. 사용자가 구현 중 확인된 공개 이벤트 전달 확장점 부족에 대해 최소 공통 확장을 승인했다. 단일 Gateway 이벤트 소스와 고정 api-remotes 목록 때문에 Studio 변경 알림을 추가할 수 없는 제약을 해소하는 효과 수명 기반 범용 등록 API, 관련 회귀 테스트와 문서를 범위에 포함한다. 공통 패키지에 Studio 이벤트를 하드코딩하거나 실행 코어를 변경하지 않는다.

## 구현 소유자

- [등록 소유자](../../packages/workflows/src/component-registry.ts)는 컴포넌트·시스템 선언과 disposer, 카탈로그 리비전, Host 의미 검증기를 소유한다.
- [문서 타입](../../packages/workflows/src/workflow-types.ts)은 메인 역할·시스템 인스턴스·연결과 위치별 진단을 표현한다.
- [저장 소유자](../../packages/workflows/src/drafts.ts)는 문서 형식과 revision을 검증하고 의미 오류와 미해석 설정을 보존한다. 조합 판정은 [공통 검증기](../../packages/workflows/src/validation.ts)의 책임이다.
- [Client 연결](../../src/workflows.tsx)은 Remote API를 제공하고 [편집기](../../src/workflow-editor.tsx)는 초안·카탈로그·검증 요청의 상태를 구분한다. [폼](../../src/workflow-forms.tsx)은 현재 등록으로 해석 가능한 설정과 연결 선택을 표시한다.

## 문서와 등록 정의

컴포넌트의 기존 `id`는 등록 종류를 가리킨다. 각 컴포넌트에는 별도의 `instanceId`를 추가한다. 시스템 인스턴스는 `instanceId`, 등록 `id`, `version`, `config`를 갖고 워크플로우 소유 배열 `systems`에 저장한다. `connections`의 각 항목은 안정적인 ID와 출발·도착 endpoint를 갖는다. Endpoint는 컴포넌트 또는 시스템을 구분하는 태그, 인스턴스 ID, 포트 ID로 구성한다. 메인 역할 구조는 유지한다. 인스턴스·연결 ID는 branded opaque ID이며 배열 재정렬과 이름 변경으로 바뀌지 않는다.

등록은 컴포넌트와 시스템을 구분한다. 컴포넌트는 필요한 시스템의 ID·정확한 버전, 허용 범위, 설정 필드, 포트를 선언한다. 시스템은 설정 필드, 포트, 지원 실행 위치를 선언한다. 이번에는 역할 컴포넌트와 워크플로우 소유 시스템만 지원하며 실행 위치는 DSH 내부만 지원한다. 선언 가능한 위치와 현재 지원 여부는 구분하고, 지원하지 않는 위치를 DSH 내부로 대체하지 않는다. 추가 범위 종류와 임의 역할 대상은 후속이다.

포트는 ID, 입력 또는 출력 방향, 의미 식별자, 허용 상대 등록 ID, 최소·최대 연결 수를 선언한다. 연결은 출력에서 입력으로만 가능하며 의미 식별자는 정확하게 일치해야 한다. 암묵적 변환·실행 순서·스케줄링을 도입하지 않는다. 기능별 추가 검증이 필요한 경우 Host 전용의 동기 의미 검증기를 등록하고 동일한 진단 형식을 반환한다. 검증기는 설정을 변경하거나 실행 부작용을 만들지 않는다. Client 카탈로그에는 직렬화 가능한 선언만 전달한다.

중복 등록 ID, 중복 필드·포트 ID, 잘못된 버전, 모순된 연결 수와 선언은 등록 시 거절한다. 컴포넌트와 시스템의 ID 공간은 구분한다. 아직 등록되지 않은 의존 대상 자체는 선언 거절 사유가 아니며 현재 가용성의 진단이다. 필요한 시스템은 같은 워크플로우에 구성되어 있고 해당 버전의 등록도 가용해야 충족된다.

## 기존 데이터 호환성

저장 계층의 [현재 제약](../../../packages/storage/storage-domain/README.md)은 domain 버전 변경의 자동 마이그레이션을 제공하지 않는다. 단순한 버전 증가로 기존 초안을 열 수 없게 만들지 않는다. 기존 domain 버전에서 legacy 문서와 명시적인 새 문서 버전을 구분하는 읽기 스키마를 사용하고, 구 문서에는 결정적인 인스턴스 ID와 빈 시스템·연결 배열을 부여한다. 변환 ID는 저장된 draft ID와 원래 항목 위치로 결정하며 변환 후에는 위치에 의존하지 않는다.

조회는 데이터를 다시 쓰지 않는다. 기존 revision을 유지한 정규화 결과를 반환하고 다음 명시적 저장에서 optimistic concurrency 확인과 함께 새 형식으로 저장한다. 다시 열거나 재시도해도 아직 저장되지 않은 변환 ID가 바뀌지 않아야 한다. 이름·지침 순서·미해석 설정은 보존한다. 손상된 문서를 빈 초안으로 대체하지 않으며 저장 실패·불명 상태는 기존 소유자의 처리를 따른다. 새 형식을 구 코드가 읽는 downgrade는 지원하지 않는다. 구현 시 영속 타입 변경 검토와 사용자에게 보이는 저장 동작 변경의 업그레이드 안내를 포함한다.

## Host 판정과 Client 동기화

하나의 공통 검증기가 문서와 분리된 카탈로그 snapshot을 입력받아 결과를 반환한다. 결과는 카탈로그 리비전, 구성 검증 통과 여부, 순서가 결정적인 진단 목록을 포함한다. 진단은 안정적인 code, 원인 항목 종류·인스턴스 또는 연결 ID·필드 경로, 관련 대상 ID와 현지화에 필요한 세부 값을 갖는다. UI 문자열을 Host에서 조립하지 않는다. 참조 누락·버전 불일치·시스템 누락·방향·의미·연결 수·범위·미지원 실행 위치와 기능별 진단을 구분한다.

Host의 문서 형식 검증은 저장과 검증 요청의 wire 입력에서 수행한다. 형식은 유효하지만 조합이 잘못된 문서는 저장 가능하다. 진단을 저장 성공과 합치지 않으며 네트워크 실패는 구성 오류로 표시하지 않는다. 후속 적용 adapter는 UI가 받은 과거 성공 결과를 신뢰하지 않고 동일한 검증기를 현재 카탈로그로 호출해야 한다. 이번에는 공개 Host 검증 진입점과 Remote 소비자의 결과 일치로 재사용을 확인하며 실제 적용 성공을 주장하지 않는다.

등록 추가·해제마다 Host 카탈로그 리비전을 증가시키고 Cordis 이벤트를 기존 Typert Remote 이벤트 경로로 전달한다. api-remotes의 `remoteEventContributions.register(event)`는 일반 `void` 알림을 기존 단일 Gateway 소스에 추가하는 효과 수명 기반 공개 확장점이다. 내장·동적 중복 이벤트는 거절하며 등록 해제는 현재와 이후 스트림의 새 전달을 중단한다. Studio는 이 API를 주입받아 카탈로그 이벤트를 등록하고 Client-safe 타입에서 동일 이벤트 선택을 선언한다. Client는 알림 구독 후 snapshot을 조회하고, 재연결 시에도 재조회한다. 늦게 도착한 응답이 최신 리비전이나 편집 요청의 진단을 덮어쓰지 않도록 구분한다. 알림은 초안 재로딩이나 편집기 재마운트를 일으키지 않는다. 변경 시 현재 편집 중인 문서를 다시 검증하며 확인 중·연결 실패·가용성 불명 상태를 표시한다. 가용성이 확인되지 않은 기능의 새 추가를 허용하지 않는다.

등록 해제는 저장된 초안과 편집 중인 값을 변경하지 않는다. 해제 전 snapshot으로 시작한 검증 결과는 그 리비전의 결과일 뿐 현재 가용성의 보장이 아니다. 오래된 disposer는 재등록된 항목을 제거하지 않으며 서비스·화면 해제 시 구독과 진행 중 요청의 결과 적용도 종료한다. 항목의 명시적 삭제 후 남은 연결은 자동 삭제하지 않고 참조 누락 진단으로 남겨 사용자가 수정하거나 삭제할 수 있게 한다.

## 구현 단계

단계 ID는 이 이슈 안에서 고정한다. 전체 구현과 이슈 범위 수용 검증은 4/4 완료했다. S1의 저장·등록, S2의 공통 검증·실제 Loader/Gateway 이벤트, S3의 폼·응답 경쟁, S4의 격리 브라우저·문서·독립 리뷰를 확인했다. 전체 회귀의 남은 실패는 이슈 수용 증거와 구분해 기록한다.

| ID | 결과와 변경 책임 | 선행·제약 | 수용 조건과 검증 |
|---|---|---|---|

## 준비 결과와 미룬 항목

위 결정은 개별 선택과 남은 결정의 권장안 채택에 따라 확정했다. 구현을 막는 제품 결정은 남아 있지 않다. 구체적인 TypeScript 보조 타입·폼 배치는 이 계약 안에서 구현 시 결정한다. 공개 API로 실현할 수 없는 제약이 발견되면 해당 단계에서 멈추고 명세를 다시 검토한다.

실제 실행·모델 호출·권한 enforcement·프리셋 활성화, 임의 역할 편집, 그래프 캔버스, 원시 JSON 편집, 버전 자동 변환, downgrade는 이번 범위 밖이다. 모델 입력 변경이 없으므로 라이브 모델 호출은 이번 수용 증거에 포함하지 않는다. 사용자 출력 snapshot과 키 없는 Loader·브라우저 검증은 모델 실행 또는 설치 앱 검증의 대체물이 아니다. 실행 프로필 배포와 기존 GUI의 검증은 별도 승인·실행 기록을 요구하며, 구현 완료 보고에서 미실행이면 명시한다.

## 후속 수정 항목

구성 검증과 실행 지원은 별개다. 현재 통과 문구인 “구성 검증 통과 — 실행 지원 미확인”은 실행 기능이 있으나 검사하지 않은 상태로 오해할 수 있다. 실행 연결을 지원하기 전의 개선 문구는 “구성에 문제가 없습니다. 워크플로우 실행은 아직 지원하지 않습니다.”로 기록한다. 이번 마무리에서는 문구를 변경하지 않는다. 후속 UI 수정 시 [Workflow 문구 사전](../../src/workflow-locales.ts)의 ko/en/zh와 소유 출력 snapshot을 함께 갱신하고, 실행 기능 도입 시 실제 지원 상태에 맞춰 다시 검토한다.

현재 메인 역할은 하나 필수이고 지침 컴포넌트는 선택 사항이다. 실행 연결 시 검토할 방향은 지침 컴포넌트가 없으면 Studio가 지침을 덮어쓰지 않고 DSH 기본 지침 구성을 사용하는 것이다. 컴포넌트가 있으면 사용자 지정 가능한 역할 지침에 반영하되 코어의 도구 사용·런타임 필수 지침은 유지한다. 이는 아직 구현된 실행 동작이 아니며, 후속 실행 명세에서 DSH의 실제 지침 조합 지점과 빈 문자열 처리·추가 또는 대체 규칙을 확정하고 검증한다.

## 검증 기록

등록과 UI의 공개 관찰 지점에서 먼저 실패하는 테스트를 실행했다. 의존성 설치와 `pnpm --dir studio run prepare:types`가 성공했다. 전역 영속 타입 검사는 63개 루트가 기존 13개 이력과 일치하고 변경 대상이 없음을 확인했다. Studio 자체 domain 호환성은 소유 저장 테스트로 검증한다. 최종 공통 확장 반영 후 `pnpm run doc-sync`는 42개 gate가 통과했고 repository references의 명세 내 커밋 해시 금지 1건이 실패했다. 해당 참조를 문서 도입 커밋의 부모로 바꾸고 `pnpm run verify-repository-references`를 다시 실행해 통과했다. 따라서 최종 파일에 대해 43개 gate의 통과 증거가 있으며, 한 번의 aggregate 실행 전체가 성공했다고 표시하지 않는다.

요청에 따라 전체 저장소 `pnpm run test`를 한 차례 실행했다. 결과는 1,960개 파일 통과, 5개 파일 실패, 25개 파일 skip이며 41,528개 테스트 통과, 30개 실패, 예상 실패 1개, skip 246개와 처리되지 않은 오류 1개다. 변경 범위 밖 worktree 테스트에서 Apple Git 2.39.5가 `--no-lazy-fetch`를 거절했다. SSH helper의 소켓 경로 제한 테스트도 실패했고, Node 26.10.0은 plugin-manager 테스트의 GC 시 미종료 FileHandle을 오류로 보고했다. 전체 테스트 성공으로 간주하지 않는다. Studio 집중 검증과 별도로 남은 환경·기존 코드 진단 항목이다.

최종 Studio 저장·등록·공통 검증·렌더링 UI·실제 Loader의 focused Node 검증은 30/30 통과했다. Host/Client runtime과 Web assets 빌드 및 Studio strict typecheck·빌드는 성공했다. 실제 Loader는 Host/Remote 판정 일치와 Gateway `$events`의 등록·해제·재등록 알림을 검증했고 1/1 통과했다. api-remotes 이벤트 회귀 검증은 6/6 통과했다. Studio 전체 Node 검증을 저장소 루트에서 실행했을 때 81개 중 79개가 통과하고 experiments-runtime의 scope 테스트 2개가 실패했다. Studio 작업 디렉터리의 공식 artifact-plane launcher에서는 해당 테스트가 통과했고 전체 81개 중 80개가 통과했다. 남은 preset-persistence 실패는 임시 프로필의 `@deepseek-ai/dsh-agent-preset` import 실패로 등록이 unknown 상태가 된 경우이며 이 변경의 파일이 아니다. 루트 실행은 소스 별칭과 built imports를 혼용하므로 Studio 검증의 기준 launcher로 사용하지 않는다. 격리 Chrome 브라우저의 최종 workflow 수용 검증은 1/1 통과했다. 의미 오류 저장, 정상 연결, 실제 제공자 해제·재등록 중 미저장 값 보존, 저장·재열기, 시스템 삭제 후 연결 진단과 재지정, 기존 서비스 탐색, 720px 좁은 폭과 라이트·다크를 확인했다. 최초 브라우저 실패는 값 입력 후 textarea의 접근성 이름이 변한 문제와 테스트 제공자 overlay의 insert 누락을 수정했다. 실제 필드에는 안정적인 접근성 이름을 추가했고 테스트 fixture는 정식 patch 형식으로 고쳤다. 최초 전체 브라우저 실행의 다른 50개 테스트는 통과하고 2개는 skip이었다.

기준 커밋부터의 작업 트리와 새 파일을 대상으로 Standards·Spec 독립 리뷰를 수행했다. Standards는 지적 0개다. Spec은 서로 호환되는 두 독립 연결 쌍 사이를 선택할 수 없는 폼과 제공자 누락 시 연결 위치 진단 부재, 두 가지 P2를 확인했다. 두 지적 모두 회귀 테스트와 독립 재리뷰로 수정 확인했으며 남은 확정 지적은 없다. 연결 쌍은 양 끝점을 함께 변경해 독립 호환 그룹 간 이동을 허용하고 연결 ID를 유지한다. 제공자 부재 시 설정을 임의로 해석하지 않고 같은 버전 복귀까지 보존하는 동작은 읽기 전용 표시 요구와 일치함을 확인했다.

라이브 모델과 기존 설치 GUI·프로필은 검증하거나 변경하지 않았다. 구현 후 별도 사용자 요청으로 이 작업 트리의 전체 런타임과 Studio를 빌드하고, 작업 트리 내부 `studio/.dsh-home`의 개발용 Web 프로필에 설치해 별도 localhost 서버를 실행했다. 인증 후 HTTP 200 응답을 확인했고 사용자가 화면에서 기능을 확인했다. 이 개발용 설치는 기존 GUI에 대한 배포가 아니다.
