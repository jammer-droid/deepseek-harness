# #18 Studio 소유 프리셋 적용과 모델·지침 실행

- 기준 브랜치: `studio/feat/workflow`. 조사 시작 HEAD: `2f929c3d154bbb5b181c31c3eab39661822283ed`.
- GitHub 선행 관계: [#17](https://github.com/jammer-droid/deepseek-harness/issues/17)은 closed다. 후속 [#19](https://github.com/jammer-droid/deepseek-harness/issues/19)가 #18을 기다린다. #18 본문 외 별도 댓글은 없으며 공통 구조 계약은 [#15 구조 검토 댓글](https://github.com/jammer-droid/deepseek-harness/issues/15)과 [구조 검토](../workflow-architecture-review.md)를 따른다.

## 목적과 지원 범위

검증한 초안의 적용본을 Studio가 별도로 저장하고, Studio 소유 프리셋으로 등록하여 새 대화의 실제 모델 요청과 지침에서 확인한다. 초안 저장, 적용본 저장, 프리셋 활성화, 실제 실행은 별개 사실이다.

사용자가 확정한 첫 실행 범위는 활성 `studio.instructions` 블록의 문서 순서대로 추가다. 메인 역할의 모델·추론 설정은 D1-a 결정에 따라 적용본에 보존하고 새 대화에서 불일치를 경고하지만, 실제 요청 route를 Studio가 강제하지 않는다. 다른 역할은 적용본에 보존하지만 실행·위임 지원으로 표시하지 않는다. 다른 역할로의 위임과 루트의 늦은 자식 구성 고정은 #19에서 다룬다. 시스템 프롬프트의 임의 교체·제거, adapter가 없는 활성 컴포넌트·시스템은 적용을 거절한다. 비활성 인스턴스와 그에 닿는 연결은 실행 구성에서 제외하되 저장한 설정과 연결은 보존한다.

기존 General 프리셋 편집기, managed delegation, 원본·기본 프리셋과 기존 저장 데이터는 변경하지 않는다. 코어 변경, 프로필 파일 직접 쓰기, 새 실행 엔진, 전역 기본 프리셋 변경, 과거 플러그인 코드 복원, 자동 데이터 이행은 범위 밖이다.

### 명세 검토: rc.2 선언 대조 결과

[DSH 재사용 조사](../dsh-reuse-investigation.md)에서 rc.2 공개 선언·배포 JS와 이 명세를 대조했다. 실행 검증이 아니며 S1에서 실제 Loader로 확인한다.

| 항목 | 확인한 사실 | 명세 영향 |
| --- | --- | --- |
| B1 등록·갱신 | rc.2 `agentPresets.register()`는 등록 즉시 mount하고 disposer를 반환한다. 같은 ID는 거절하므로 갱신은 "이전 disposer → 새 등록"이다. 이전 generation은 묶인 agent가 0이 될 때까지 유지된다. 활성화 실패는 `list()`의 `broken` 진단이다. | 기존 실행 보존은 선언·구현 수준에서 지지된다. 갱신 사이에 ID가 없는 구간이 있어 새 대화 생성이 `not-found`로 실패할 수 있다. S1에서 확인하고, 실패 시 UI가 재시도를 안내한다. |
| 재개 | Session resume은 기록된 preset ID로 **현재** 정의에 mount한다. | 재적용 후 재시작·재개한 오래된 세션은 새 구성을 받는다. "재시작 시 과거 구성 미보장"을 UI 제한으로 표시한다(#19와 공유). |
| **B3 메인 모델** | preset 정의에는 모델 필드가 없다. 세션 생성은 `installModelSelection`을 preset mount보다 **먼저** 설치하므로, 세션 선택값(미선택 시 전역 기본 모델)이 요청 route를 바깥에서 덮어쓴다. preset 안의 `agent/request` 재작성은 효과가 없다. 최외곽(`prepend`) 재작성은 요청은 바꾸지만 UI·`{{model}}`이 어긋나고 매 step 모델 변경 알림을 추가한다. `sessionController.selectModel`은 전역 기본 모델도 저장한다. | "메인 역할 provider/model/reasoning이 실제 요청에 반영"을 공개 API만으로 부작용 없이 충족하는 경로가 확인되지 않았다. 아래 B3으로 기록하고 D1-a로 범위를 줄였다. |

기존 조사 문서의 '등록 기반 편집 모델이 없다' 등 과거 현황은 현재 소스와 다르다. 현재 편집·저장 사실은 위 소스를 우선하고, 구조·제품 요구는 [제품 명세](../workflow-specification.md)를 따른다. 이번 준비에서는 소스·문서·GitHub·read-only Inspect만 확인했으며 테스트, 빌드, 설치, 모델 호출은 실행하지 않았다.

## 확정 계약

### 소유권과 적용 입력

Studio가 초안과 별도의 프로필별 적용본을 소유한다. 적용본은 원본 초안 식별자·리비전, 적용 리비전, 실행에 필요한 독립 구성과 등록 상태를 구분한다. 같은 워크플로우 재적용은 같은 논리 Studio 프리셋을 갱신하며 사용자 프리셋 이름 충돌로 타 소유 프리셋을 대체하지 않는다. 표시 이름은 식별자가 아니다.

적용은 저장된 초안의 명시적 리비전과 관측한 적용 리비전을 대상으로 한다. 미저장 편집을 몰래 저장하거나 실행하지 않는다. Host가 최신 카탈로그·모델·adapter 지원을 다시 검사하며 충돌 시 쓰기 전에 거절한다. 검증 중 제공자가 해제되거나 카탈로그가 바뀌면 오래된 검증 결과로 진행하지 않는다. UI는 Host 판정을 재구현하지 않는다.

등록 API와 그 disposer는 Studio 플러그인 수명에 귀속된다. Studio 해제·재등록은 새 선택 가용성 및 진행 중 실행에 미치는 영향을 검증해야 한다. 임의의 Host 서비스나 비공개 레지스트리 필드에 접근하지 않는다.

### 저장·활성화·결과 불명

적용본 저장이 확인된 뒤 등록·활성화를 시도하며 UI는 각각을 구분한다. 저장 전 거절은 기존 적용본과 프리셋을 바꾸지 않는다. 저장 뒤 활성화 실패는 '저장됨 / 활성화 실패'로 남기고 저장 실패 또는 전체 성공으로 축약하지 않는다. 이전 정상 프리셋의 유지·복구는 실제 상태를 확인한 경우에만 표시한다.

동시 적용은 관측 리비전으로 충돌을 검사하고 프로필 내 쓰기를 직렬화한다. 응답 유실은 클라이언트의 결과 불명이지 실패 확정이 아니다. 재조회가 초안·적용 리비전과 실제 등록 상태를 대조할 수 있어야 하며, 확인 없이 동일 요청을 재실행하거나 새 적용 리비전을 만들지 않는다. 저장 소유자가 내구성 결과를 확정하지 못한 경우 후속 쓰기·활성화를 중단한다.

재시작 시 저장된 최신 적용본의 지원 여부를 다시 확인하고 등록한다. 불명·실패 기록을 무조건 성공으로 승격하지 않는다. 과거 코드와 과거 실행 복원을 보장하지 않으며 새 대화 실행과 재개를 같은 검증으로 취급하지 않는다.

### 메인 실행과 격리

기존 프리셋 선택·새 대화 흐름을 재사용한다. 메인 역할의 provider/model/reasoning은 DSH 세션 모델 선택이 소유한다(D1-a). Studio는 적용본의 메인 모델과 새 대화의 실제 요청 route(`request/header`)가 다르면 Workflow 화면과 적용 상태에 불일치 경고와 모델 선택기 사용 안내를 표시한다. 전역 기본 모델·세션 선택을 Studio가 바꾸지 않는다. Studio preset agent에도 experiments 정책이 그대로 적용되며(D2), 적용본 설명에 적용 시점의 실험 설정 대상 여부를 표시한다. 지침은 활성 블록의 문서 순서대로 추가하며 DSH 필수 지침·권한을 대체하지 않는다.

재적용은 새 루트에 반영하고 살아 있는 기존 메인 실행의 모델·지침은 바꾸지 않는다. 다른 워크플로우·원본 프리셋·병렬 실행에 전역 변경이 새지 않아야 한다. 공유 플러그인 인스턴스에 실행별 가변 상태를 두지 않는다. 늦은 자식 및 재시작 시 실행 전체 고정 정책은 #19의 미결정 사항이며 이 문서에서 확정하지 않는다.

## 안정적인 구현 단계

새 계획 S1–S5를 정의한다. 기존 #18 단계가 없으므로 재번호·분할·병합은 없다. 의존 순서는 S1 → S2 → S3 → S4 → S5다.

| 단계 | 결과·선행 | 변경 책임과 제약 | 관측 가능한 수용 조건·검증 |
| --- | --- | --- | --- |
| S1 | Desktop 기준 공개 등록 경로의 적합성. 선행 #17 완료. | Studio 소유 Loader fixture 및 국소 DSH adapter 후보. rc.2 공개 타입·exports를 직접 확인하고 현재 Web에서도 같은 경로 확인. 코어·기존 프로필 수정 금지. | 실제 Loader에서 새 ID 등록, 같은 논리 프리셋 갱신, 새 대화 반영, 기존 메인 실행 보존, 중복 ID 거절, 활성화 실패 진단, disposer·재등록을 확인한다. 저장 후 실패 시 이전 정상 구성의 실제 상태도 확인한다. rc.2가 불가능하면 차단 사유·대안만 보고한다. |

S1은 공개 지원 경로를 확인하는 구현 첫 단계이며 본 문서 작성 중 테스트를 실행했다는 뜻이 아니다. 필요한 런타임 산출물이 없으면 준비물과 막힌 검사를 보고하고 전체 코어 빌드를 자동 실행하지 않는다. Web workspace 회귀는 Desktop 독립 설치 증거를 대신하지 않는다.

## 차단 조건과 해소 기준

- **B1: rc.2 공개 API의 프리셋 갱신·수명 계약 미검증.** 현재 Web `register()` 존재만으로 rc.2 호환을 확정할 수 없다. S1에서 동일 논리 프리셋의 실제 등록 방식, 안전한 ID 소유권, 갱신 시 이전 활성 구성의 처리, 모델·지침 공개 연결 지점을 확인하고 그 결과를 이 문서에 기록해야 한다. 기존 메인 실행 보존·새 대화 반영이 불가능하면 구현을 중단하고 범위 결정을 요청한다. 프로필 직접 쓰기나 Web 전용 API로 대체하지 않는다.
- **B3 (해소): 메인 역할 모델의 공개 적용 지점 없음.** 사용자가 권장안 **D1-a**를 선택했다. #18은 지침만 실제 적용하고, 메인 모델은 적용본 보존과 불일치 경고로 다룬다. 공개 API만 쓰고 전역 설정을 바꾸지 않는다. 기각한 대안: 최외곽 `agent/request` 재작성(UI·`{{model}}` 불일치, 매 step 모델 변경 알림 누적), 생성 직후 `selectModel`(전역 기본 모델 변경). **결과: 이슈 수용 조건의 "실제 요청이 적용된 모델 반영"과 A3의 실행 측면은 #18에서 충족하지 않는다.** 위임 child의 역할 모델은 #19에서 child `agent/request` 재적용으로 강제한다. 메인 모델 강제는 공개 API가 생기면 후속으로 다룬다.
- **D2 (결정): experiments 정책.** 사용자가 권장안을 선택했다. Studio preset agent에도 experiments 정책을 그대로 적용하고, 적용본 설명에 적용 시점 실험 대상 여부를 표시한다. experiments 패키지는 변경하지 않는다.
- **B2: 독립 배포와 실제 실행 증거 없음.** S5에서 실행 경로·런타임 버전·Studio 패키지·명령·결과를 기록한다. 이는 구현 완료 조건이며 S1 착수 자체를 막지는 않는다.
- #19의 자식 실행 고정·재개 정책, #20 도구 제한, #21 권한·컨텍스트, #22 독립 정의·템플릿은 각 이슈 명세([#19](19-workflow-delegation.md), [#20](20-workflow-tools.md), [#21](21-workflow-access-context.md), [#22](22-workflow-library.md))가 소유한다. #18의 S2 compiler는 #19–#21이 adapter를 추가하는 확장 지점이다.

D1·D2는 결정됐고 S2–S5에 남은 사용자 결정은 없다. S1에서 B1이 해소되면 `ready`로 전환한다. 실패 보장이나 사용자 동작이 달라지는 대안을 발견하면 자동 채택하지 않고 사용자에게 확인한다. 구현 handoff는 `$lean-implementation` Guide에서 S1부터 시작한다.
