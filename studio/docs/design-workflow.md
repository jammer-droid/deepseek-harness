# Studio 이슈 작업 절차

## 요약

이 절차는 Studio 개발에만 적용한다. GitHub 이슈를 읽고 필요한 구현 결정을 이슈별 문서에 기록한 뒤, 검증 가능한 단계로 구현한다. 기준 브랜치 통합 이후는 [마무리·배포 절차](release-workflow.md)를 따른다. 저장소 전체 개발 절차를 새로 정의하지 않는다. 트래커와 라벨은 기존 [트래커 설정](../../docs/agents/issue-tracker.md)과 [라벨 설정](../../docs/agents/triage-labels.md)을 따른다.

## 문서 위치와 소유권

- 이 문서가 Studio의 이슈별 설계 절차를 소유한다. Studio 작업에서는 사용자가 지정한 이 문서를 사용하며 별도의 전역 설계 설정 파일을 생성하지 않는다.
- 이슈별 문서는 `studio/docs/issues/<번호>-<짧은-이름>.md`에 한국어로 작성하고 [명세 색인](issues/README.md)에 등록한다. 이슈 번호가 문서 식별자이며 기존 문서가 있으면 갱신한다.
- GitHub 이슈는 사용자 결과, 완료 조건, 선행 관계, 진행 상태를 소유한다. 구현 명세는 선택한 동작·소유권·제약과 구현 단계·검증 증거를 소유한다. 제품 공통 요구와 구조는 기존 [문서 목차](README.md)의 소유 문서를 참조한다.
- 명세 준비 상태는 `draft`, `ready`, `blocked`다. 완료 여부는 별도 완료 기록으로 남긴다. 이 상태를 GitHub 라벨이나 이슈 상태로 자동 변환하지 않는다.
- 간단한 수정은 중요한 미결정 사항이 없으면 명세 없이 진행할 수 있다. 공통 규칙과 이슈별 내용은 별도 문서로 유지하고 모든 작업을 한 문서에 누적하지 않는다.

## 명세 준비

1. 실제 이슈 본문·댓글·선행 관계와 관련 소스·테스트를 읽는다. 이슈 URL, 목적, 범위, 제외 범위, 기준 브랜치와 시작 커밋을 기록한다.
2. 기존 문서를 찾아 재사용하고 제품 명세와 현재 구현의 차이를 기록한다. 구조 검토를 새로 복제하지 않는다.
3. 동작, 상태 소유권, 수명, 저장·실패 보장 및 호환성을 결정한다. 사용자 선택이 필요한 중요한 사항은 추천안과 차이를 제시하고 확정 전에는 미결정으로 표시한다.
4. `S1`, `S2`처럼 안정적인 단계 ID를 부여한다. 각 단계에는 결과, 선행 단계, 변경 책임, 수용 조건과 검증 방법을 기록한다. 분할·병합·순서 변경 시 ID를 조용히 재사용하지 않는다.
5. 모든 중요한 결정이 확정되거나 명시적으로 범위 밖이면 `ready`로 표시하고 첫 단계를 지정한다. 시작을 막는 조건이 있으면 `blocked`와 해소 조건을 기록한다. 그 외에는 `draft`다.

명세는 위 내용을 담는 간결한 문서로 작성하며 별도의 빈 템플릿 복사본은 유지하지 않는다. 준비 완료가 구현·커밋·푸시·이슈 변경 권한을 자동 부여하지 않는다.

## 구현과 검증

DSH 업데이트 뒤 호환성 경고·설치 차단·실행 실패를 다룰 때는 [호환성 오류 대응](development/dsh-compatibility-response.md)을 따른다. 원인 조사부터 격리 검증·승인된 Desktop 반영·복구까지의 완료 기준을 정한다.

각 단계의 결과를 작은 단위로 구현하고 해당 수용 조건을 검증한 뒤 다음 단계로 진행한다. 현재 단계와 전체 진행을 명세에 유지한다. 영향에 맞는 단위·실제 Loader·모델 및 사용자 출력 스냅샷·UI 검증을 선택하고, 실행한 검사와 미실행 항목을 구분한다. 라이브 모델, replay, 설치 앱 검증을 서로 대신했다고 표시하지 않는다.

사용자의 별도 변경을 포함하거나 덮어쓰지 않는다. 다른 작업의 미커밋 변경이 있으면 승인된 기준 커밋에서 별도 worktree를 사용한다. 같은 worktree의 변경을 여러 세션이 동시에 수정하지 않도록 작업 위치를 명시한다. 실행 프로필 변경과 배포는 구현 검증과 분리한다.

## 모든 Studio 이슈의 독립 배포 완료 조건

명세 작성 시 대상 DSH 버전과 공개 API 요구를 기록한다. 본체 수정이 필요한 설계는 구현 전에 차단하고 지원 제약이나 Studio 내부 대안을 명시한다. 코어 원복은 사용자 승인된 정리 작업에만 허용한다.

구현 완료 판단에는 Studio 범위 검사, 변경 기능 테스트, Studio 타입 검사·빌드 결과와 독립 설치 결과를 구분해서 기록한다. 독립 설치는 workspace 코어 대신 수정하지 않은 지정 버전 DSH를 사용하고, 패키징한 Studio를 격리 home/profile에 설치하여 Loader 로딩과 변경한 사용자 흐름을 확인한다. 런타임 버전·실행 경로·Studio 패키지·명령·결과를 남긴다. 코어 재빌드, 수정한 workspace 또는 개발 scaffold 결과는 이 증거를 대신하지 않는다. 대상 버전에서 API가 없거나 설치 검증이 막히면 해당 단계는 blocked로 남긴다.

독립 설치 이후의 E2E는 [에이전트 E2E 검증 지침](../scripts/agents/README.md#기본-흐름)의 기본 흐름(격리 서버 → L0 스크립트 → L1 `judge`·`pixie_loop` → L2 검증자 판단)을 따른다. 이슈마다 지침서(`scripts/agents/issues/<이슈 번호>-<주제>.md`)를 만들어 새 세션의 검증자가 실행하고, 결론으로 남길 기록만 `docs/verification/`에 옮긴다. 이슈가 끝나면 지침서를 `scripts/agents/archive/issues/`로 옮긴다.

전체 저장소 빌드·테스트·문서 번역을 자동으로 실행하지 않는다. 필요한 Studio 검증만 선택하며, 외부 준비물이나 범위 밖 작업이 필요하면 이유와 범위를 설명한다. 이후 이슈도 이 조건을 그대로 적용하며 기존 명세에 전체 저장소 절차가 남아 있으면 이 절차에 맞춰 정정한다.

## 완료와 브랜치 통합

1. 이슈의 모든 수용 조건과 단계별 검증 결과를 확인한다. 미해결 실패·지원 공백이 있으면 완료로 표시하지 않는다. 현재 제품 동작은 관련 README·API 문서·테스트에 반영하고 명세에는 완료 결과와 남은 제한을 기록한다.
2. 기준 브랜치 병합부터 배포·GitHub 이슈 종료까지는 [마무리·배포 절차](release-workflow.md)를 따른다. 각 단계는 해당 작업의 승인 범위에서만 수행하며, 이 절차 자체가 병합·푸시·배포·이슈 종료 권한을 주지 않는다.
3. 다음 이슈는 갱신된 기준 브랜치에서 새 브랜치로 시작하고 이 절차와 기존 명세를 재사용한다. worktree·브랜치 정리는 미커밋 변경과 보존할 파일이 없는지 확인하고 별도 승인 범위에서 수행한다.
