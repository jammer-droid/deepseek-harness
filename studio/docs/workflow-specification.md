# Studio 워크플로우 기능 명세서

## 요약

이 문서는 사용자가 합의한 목표와 첫 구현 의무를 구분하는 설계 명세다. 현재 구현을 설명하는 API 레퍼런스가 아니며 구체적인 저장 스키마·서비스 이름·실행 프로토콜은 구현 설계에서 확정한다. 제품 목적은 [기획서](workflow-product-plan.md), 현재 지원 근거는 [구성 조사](workflow-composition-research.md)와 [실행 조사](workflow-runtime-research.md)를 참조한다.

## 범위와 우선순위

| 구분 | 의미 |
| --- | --- |
| 첫 구현 | 기존 DSH 기능을 사용해 개발 팀 템플릿을 조립·편집·실행하기 위한 기능 |
| 조건부 | 제품 요구는 합의했으나 현재 DSH 지원 범위가 제한되어 실제 제공 항목을 검증해야 하는 기능 |
| 후속 | 이번에는 구현하지 않고 요구사항만 보존하는 기능 |

자율성이 기본이다. 명세에 제어 설정이 등장하더라도 모든 행동에 중앙 규칙을 추가하라는 뜻은 아니다. 첫 구현은 DSH에 없는 큐·스케줄러·실패 전파·복구 엔진을 만들지 않는다. 지원 공백은 사용자에게 표시하고 미지원 항목을 성공한 설정처럼 저장·적용하지 않는다.

## 구성 및 등록 모델

### 엔티티와 재사용

- 독립 에이전트 정의를 저장하고 워크플로우에 복사할 수 있다. 메인도 동일한 에이전트 편집 모델을 사용한다.
- 워크플로우는 포함된 역할, 메인 역할, 컴포넌트 조합, 시스템 구성과 필요한 연결을 보유한다.
- 동일 역할의 여러 실행 인스턴스는 서로 구분된다. 역할 정의 수정은 이미 생성한 인스턴스를 변경하지 않는다.
- 이름 있는 컴포넌트 설정 템플릿을 저장·복사할 수 있다. 원본과 복사본은 live inheritance나 override 체계로 묶지 않는다.
- 원본 업데이트 가져오기와 병합은 후속이다.

### 컴포넌트 등록

기능 제공 플러그인은 최소한 안정적인 식별자, 표시 이름·설명, 설정 정의, 필요한 시스템, 적용 범위·연결 조건을 제공한다. 입출력 연결이 있는 기능은 그 입력·출력 정보도 제공한다. 기본 동작 대비 변화, 모델에 전달되는 내용, 제약을 컴포넌트 설명에서 확인할 수 있어야 한다. 현재 메인 역할·시스템·포트 연결의 최소 선언과 저장 형식은 [#16 명세](issues/16-workflow-validation.md)에 정한다. 추가 컴포넌트의 설명과 실행 연결은 각 후속 이슈에서 확장한다.

Studio는 등록 정보를 읽어 기본 편집기를 구성한다. 전용 UI는 선택적으로 제공할 수 있다. 로드 가능한 플러그인 전체를 자동으로 적합한 컴포넌트로 간주하지 않는다. 알 수 없는 컴포넌트는 초안 데이터를 보존하고 활성 상태이면 누락을 진단하며, 데이터 손실을 일으키는 자동 삭제를 하지 않는다.

편집기는 화면 진입·재진입·재연결·수동 새로고침에서 기존 Remote API로 카탈로그를 조회한다. 실시간 카탈로그 이벤트를 구독하거나 자동 polling을 하지 않으며 DSH 본체 수정이나 코어 재빌드를 요구하지 않는다. 갱신은 저장된 초안을 다시 읽지 않으므로 미저장 설정과 연결을 유지한다. 조회 실패는 표시하고 가용성이 확인되기 전까지 새 항목 추가를 막는다.

### 워크플로우 내 사용 여부

컴포넌트와 시스템 인스턴스의 `enabled?: boolean`은 문서 버전 3에 저장하며 생략하면 활성이다. 사용 안 함은 인스턴스 삭제나 전역 플러그인 해제가 아니며 다른 워크플로우에 영향을 주지 않는다. 설정과 연결은 저장·재열기 시 그대로 보존한다.

비활성 인스턴스 자체의 구성·등록·의미 검증과 그 인스턴스에 닿는 연결 검증은 생략한다. 활성 항목의 필수 시스템과 최소 포트 연결 수는 활성 항목과 연결만으로 충족해야 한다. 비활성 항목도 저장 문서 형식과 ID 중복 검사를 받으며, 재활성화하면 보존한 값이 정상 검증 대상이 된다. 실제 실행 구성에서 비활성 항목을 제외하는 처리는 후속 실행 구현의 요구사항이다.

기존 초안은 읽을 때 저장소와 revision을 바꾸지 않고 정규화하며 다음 명시적 저장에서 `roles`와 `mainRoleId`를 포함하는 v3 문서로 기록한다. 백업·모델 선택·Remote 호출자 변경과 되돌리기 제약은 [워크플로우 업그레이드 안내](workflow-upgrade.md)를 따른다.

### 시스템 등록과 실행 위치

시스템은 플러그인 코드로 구현하며 Studio에서 코드 편집 기능을 제공하지 않는다. 워크플로우는 여러 시스템을 구성할 수 있다. 시스템 구현은 컴포넌트의 조합과 연결을 읽어 동작을 수행한다. 엔티티 종류마다 Studio 내부에 기능 분기를 추가하는 방식은 피한다.

시스템은 DSH 내부, Studio 런타임, 양쪽 중 지원하는 실행 방식을 선언한다. 워크플로우는 지원되는 방식 중 시스템별로 선택한다. 양쪽 방식의 시스템을 혼합하는 것은 후속 요구이며 첫 구현은 DSH 내부 실행만 지원한다.

선후 관계와 결과 전달이 필요한 경우 워크플로우에 명시한다. 독립적인 시스템은 자체 실행 지점에서 동작한다. 입력 타입 일치만으로 실행 가능하다고 판정하지 않고 필수 서비스·권한·실행 범위도 검사한다. 연결을 편집하는 것과 시스템의 핵심 로직을 편집하는 것을 구분한다.

## 첫 컴포넌트 명세

### 모델

- 현재 사용자가 DSH에서 선택 가능한 모델 목록을 재사용한다. 미등록 모델을 Studio 전용 목록으로 제공하지 않는다.
- 템플릿 생성 시 모델을 한 번 선택하여 모든 역할의 초기값으로 복사한다. 역할별 모델·추론 설정은 이후 독립 변경한다.
- 추론 설정은 해당 모델이 지원하는 값만 허용한다. 미지정은 실제 제공자 기본 동작을 따른다.
- 후속 라우팅은 저장된 모델·추론 설정을 기본값으로 사용하되 허용 후보 중 선택할 수 있다. 선택은 생성한 인스턴스와 후속 대화에 유지하고 저장된 역할은 변경하지 않는다.

### 지침

- 이름 있는 지침 블록의 추가·편집·제거·순서를 지원한다. 뒤에 배치했다고 앞 지침을 확실히 덮어쓰는 것으로 설명하지 않는다.
- 기본 시스템 프롬프트 섹션에 추가·교체·제외하는 것은 DSH가 제공하는 지점에 한해 노출한다. 모든 내부 프롬프트를 수정할 수 있다고 보장하지 않는다.
- 지침과 권한은 다르다. 프롬프트 수정으로 sandbox나 executor 제한을 해제하지 않는다.
- 기본 개발 팀 지침은 명세 확인·구현 위임·리뷰 활용을 권장하되 필수 순서로 강제하지 않는다.

### 도구

- 기존 내부·외부 도구를 묶음 및 개별 단위로 포함·제외한다.
- 제외된 도구는 모델 노출과 실제 실행 양쪽에서 제한한다. 직접 호출 등 우회 경로도 동일한 실행 검사를 거쳐야 한다.
- 외부 도구 연결 생성·인증·관리는 이번 범위가 아니다. 현재 등록된 연결을 재사용한다.
- 파일 수정 도구 제외만으로 읽기 전용을 보장하지 않는다. 셸·외부 도구의 권한은 별도 실행 환경 제한에 따른다.

### 스폰·위임

- 메인만 위임하는 구성을 기본으로 제공하며, 재위임은 역할별 허용 대상·깊이의 지원 범위 안에서 선택한다.
- 위임 대상은 현재 워크플로우에 포함된 역할이다. 임의의 외부 에이전트 정의로 위임하지 않는다.
- Fork는 직접 스폰한 부모의 컨텍스트를 기준으로 한다. 새 컨텍스트는 부모 대화를 상속하지 않지만 역할의 지침·도구 설정은 적용한다.
- 역할별 기본 컨텍스트 방식과 허용 방식 중 호출자가 선택한다. 두 방식 모두 추가 지침을 전달할 수 있다.
- 생성한 자식에게 후속 메시지를 보내거나 새 인스턴스를 생성할 수 있다. 기존 자식에 대한 후속 대화는 새 Fork가 아니다.
- 결과 대기·백그라운드 작업은 DSH가 제공하는 동작을 사용한다. 역할별 설정으로 노출할 수 있는 정확한 범위는 실행 조사에 따른다.
- 기본 템플릿의 재작업은 기존 구현자에게 전달하도록 안내하되 고정 승인 절차를 강제하지 않는다.

### 접근 권한

- 도구 제공 설정과 실제 파일·셸·네트워크 등 자원 접근 제한을 분리한다.
- 제품 목표는 역할별 직접 작업 권한과 위임 권한의 구분이다. Host와 워크플로우가 강제하는 상한을 넘지 않는다.
- 현재 DSH가 부모 정책을 상속하는 경우, 부모보다 넓은 자식 권한을 부여할 수 있다고 표시하지 않는다. 독립 역할 권한은 조건부 요구다.
- 지원되지 않는 권한 옵션은 비활성 이유를 표시하거나 제공하지 않는다. 지침 문구만으로 접근이 차단된다고 설명하지 않는다.

### 컨텍스트

- 설정 범위는 모델이 사용할 컨텍스트 윈도우 크기와 자동 압축 시작 시점뿐이다. 압축·요약 알고리즘은 DSH 기본 기능을 사용한다.
- 값별 우선순위는 역할 명시값 → 실제 선택된 모델의 프로바이더가 제공하는 해당 기본값 → DSH 기본값이다.
- 모델 프로바이더가 자동 압축 임계값도 반드시 제공한다고 가정하지 않는다. 현재 지원 필드는 조사 근거에 따라 연결한다.
- 라우팅으로 모델이 달라지면 미지정 값은 실제 선택된 모델을 기준으로 해석한다. 명시값이 지원 한도를 넘으면 조용히 잘라내지 않고 충돌을 표시한다.
- 제품의 '컨텍스트 윈도우 크기'와 DSH의 토큰 예산·출력 예약·압축 임계값은 같은 값이라고 가정하지 않는다. 단위와 허용 범위를 구현 전에 확정한다.

## 편집·저장·적용

1. 엔티티 목록과 컴포넌트 설정 패널에서 편집한다. 그래프 편집기는 첫 구현의 필수 기능이 아니다.
2. 불완전하거나 의존성이 누락된 구성도 초안으로 저장할 수 있다. 저장은 실행 가능한 프리셋의 갱신과 분리한다.
3. 적용 시 참조, 설정, 모델 지원, 필수 시스템, 실행 위치, 연결과 권한 강제 가능 여부를 검사한다.
4. 적용 대상은 Studio 소유의 별도 사용자 프리셋이다. 기존 기본 프리셋과 일반 편집기의 타 프리셋을 덮어쓰지 않는다.
5. 같은 워크플로우 재적용은 그 프리셋을 갱신한다. 편집 중에는 기존 적용 구성을 유지한다.
6. 저장·활성화·통신 결과를 구분한다. 저장 후 활성화 실패나 결과 불명 상태를 성공으로 표시하지 않는다. 재조회로 현재 상태를 확인할 수 있어야 한다.
7. 동시 편집 충돌 시 사용자의 초안을 유지하고 최신 구성을 불러오도록 안내한다. 조용한 덮어쓰기를 하지 않는다.

초안 리비전, 적용 리비전, 활성화 상태는 구별되어야 한다. 구체적인 저장소·트랜잭션·이전 정상 구성 유지 방법은 현재 configEditor의 기존 행 수정 기능만으로 확정하지 않는다.

## 실행과 상태

메인 대화 세션 하나를 한 실행으로 본다. 후속 사용자 메시지는 같은 실행을 이어가며 하위 에이전트는 해당 실행에 소속된다. 같은 워크플로우에서 동시에 시작한 다른 실행의 진행 상태·결과가 섞이지 않는다. 공용 캐시 같은 공유 자원은 별도로 명시한다.

목표는 시작 시 구성 고정이며 이후 적용은 새 실행에 반영한다. 현재 DSH가 살아 있는 Agent에 대해 보유하는 프리셋 리비전과, 오래 실행된 루트가 나중에 생성하는 자식의 역할 설정 캡처는 별개로 검증한다. 재시작 후 과거 구성 복원은 현재 기본 프리셋 ID 복원만으로 충족하지 않는다.

재시작 후 진행 상태를 이어가고, 복구 불가능하거나 결과 불명인 작업을 표시하는 것은 목표 요구다. 첫 구현에서는 DSH의 기존 복구 동작을 재사용하며 새로운 내구성 프로토콜을 만들지 않는다. 재시작 후 동일 구성 보장을 제공하지 못하면 제한을 명시해야 한다.

동시 실행 상한·대기열·취소 전파 등은 DSH 기능 재사용을 우선한다. 초기 논의의 세부 제어를 모두 Studio 정책으로 구현하지 않는다. 하위 실패 시 전체 또는 부분 진행을 어떻게 제어할지 일반 정책을 추가하지 않고 모델과 기존 실행 체계에 맡긴다. 필수 권한 제한과 도구 실행 거부는 자율성과 별개로 강제한다.

## 후속 결정 컴포넌트

이 절 전체는 스펙만 보존하며 첫 구현에서 Jev API·도구·UI·자격 증명을 추가하지 않는다.

### Jev 입출력

호출 경로는 `POST https://api.typesafe.ai/v1/systemone`이다. 공식 입력은 `model`, `state`, 질문 ID별 `questions`다. `state`는 문자열·JSON 객체·배열로 전달하고 질문은 같은 state를 독립적으로 평가한다. 응답의 `answers`는 동일 질문 ID로 대응한다. 임의의 설명문 생성 스키마로 대체하지 않는다. 근거: [State](https://docs.typesafe.ai/concepts/state), [Quick start](https://docs.typesafe.ai/introduction/quickstart).

| 타입 | 질문 기준 | 응답 |
| --- | --- | --- |
| Choice | 선택지 이름과 설명의 map | choice, probabilities, confidence |
| Score | 2–10개 수준 설명의 순서 있는 배열 | score: 0부터 N−1까지이며 소수 가능, probabilities, confidence |
| Noul | 예/아니오 질문, 선택적인 true/false 기준 | noul: 예일 확률 0–1 |

근거: [Choice](https://docs.typesafe.ai/primitives/choice), [Score](https://docs.typesafe.ai/primitives/score), [Noul](https://docs.typesafe.ai/primitives/noul). `confidence`는 분포에서 계산한 확신도이며 정답 보장이 아니다. Noul에는 별도 confidence가 없다. 근거: [Confidence](https://docs.typesafe.ai/confidence).

### 조립 및 사용

- 코드베이스 우선순위, 요청 충분성, 모델·역할 선택 등 일반 판단에 사용한다.
- 사용처에서 state 구성, 질문·평가 기준, 결과 연결을 설정한다. 샘플 템플릿과 고급 코드 구성을 지원하는 방향이며 코드를 어디서 실행할지는 별도 설계한다.
- 결과를 코드로 처리하거나 에이전트에게 전달하여 대화하게 할 수 있고 둘을 결합할 수 있다. 부족한 정보에 관한 질문 문장 생성은 결과를 받은 대화 모델의 역할이지 Jev 기본 출력이 아니다.
- 선택적 도구 호출과 워크플로우 필수 호출을 모두 지원한다. 호출 필수와 결과에 따른 분기 강제는 별도 설정이다.
- 불확실성 경로는 사용처별로 명시한다. API 실패를 낮은 점수나 조건 미충족이라는 정상 판단으로 바꾸지 않는다.
- 강제 분기 단계는 별도 실패 경로가 없다면 성공한 판단 없이 통과하지 않는다. 이 제어는 사용자가 선택한 구성에만 적용한다.

## 후속 미리보기와 관찰

모델 없는 미리보기는 샘플 입력에 시스템의 구성·변환을 적용해 모델에 전달될 내용을 확인한다. 모델이 필요한 단계는 중단하거나 명시적으로 샘플 응답을 사용한다. 실제 파일 수정·명령 실행 등 부수 효과는 수행하지 않는다. 실제 구성된 입력과 대체 응답을 구분한다.

실행 관찰은 모델의 내부 사고가 아니라 실제 요청·도구 결과·컴포넌트 적용 기록을 대상으로 한다. 처음에는 우리가 구현하는 시스템이 기록을 제공하고, 외부 플러그인을 자동 분석한다고 약속하지 않는다. 기존 로그 참조를 재사용하며 중복 컨텍스트 저장을 피한다. 여러 변환이 있으면 단계 관계를 확인할 수 있어야 한다.

민감한 대화·코드·자격 증명이 관찰 자료에 포함될 수 있으므로 접근·보존·마스킹 정책을 설계한다. 마스킹이나 생략은 사용자에게 표시한다. 전후 변환 비교와 실제 품질·비용 성능 비교는 별개이며 A/B 모델 평가를 초기 기능으로 요구하지 않는다. DSH 코드 재사용 지점과 지원 가능한 정확한 관찰 범위는 후속 조사한다.

## 수용 기준과 검증

| ID | 첫 구현 수용 기준 | 검증 방법 |
| --- | --- | --- |
| A1 | 템플릿으로 메인·구현자·리뷰어를 만들고 같은 편집 방식으로 수정한다. | UI 및 저장 테스트 |
| A2 | 에이전트/컴포넌트 복사 후 원본 변경이 복사본에 전파되지 않는다. | 저장·복사 회귀 테스트 |
| A3 | 현재 모델 목록과 모델별 추론 옵션을 사용하고 잘못된 선택은 적용을 거부한다. | 모델 카탈로그 fixture 및 Host 검증 |
| A4 | 도구 제외는 요청 노출과 executor 호출에서 모두 확인된다. | 실제 Loader 구성·거부 경로 테스트 |
| A5 | Fork/새 컨텍스트·추가 지침·기존 자식 후속 대화가 서로 구분된다. | DSH child API 통합 및 모델 입력 스냅샷 |
| A6 | 워크플로우 밖 역할 위임은 거부되며 메인의 일반적인 작업 판단은 강제 순서에 갇히지 않는다. | 위임 대상 검증·기본 도구/지침 스냅샷 |
| A7 | 지원하지 않는 권한 및 컨텍스트 값은 허위 적용되지 않는다. | executor 권한·설정 충돌 테스트 |
| A8 | 초안 저장은 적용된 프리셋을 바꾸지 않으며 적용은 별도 프리셋만 변경한다. | 프로필/Loader 통합·동시 편집 테스트 |
| A9 | 필수 시스템 누락·플러그인 제거를 표시하고 등록 disposer가 UI/레지스트리에서 제거된다. | 실제 Loader lifecycle 테스트 |
| A10 | 실행 간 상태가 격리되며 새 적용이 살아 있는 기존 실행 구성을 변경하지 않는다. | 두 세션 및 이후 자식 생성 회귀 테스트 |
| A11 | 저장 실패·활성화 실패·통신 불명 상태를 구분한다. | 실패 주입 및 UI snapshot |
| A12 | 컴포넌트 설명에서 기본 동작 대비 변경과 제한을 확인한다. | locale별 UI 검증 |

구현 검증에는 관련 단위 테스트, 실제 Loader 비단위 테스트, 모델/사용자 출력 스냅샷을 포함한다. 실제 모델 품질 검증과 소스 fixture 검증을 구분한다. 현재 문서 작업에서는 제품 실행 성공을 검증했다고 보고하지 않는다.

제품 코드·프로필·플러그인 설치는 이 문서 작업의 범위가 아니다. 코드 구현은 위 차이를 반영한 구현 계획을 확인받은 뒤 진행한다.
