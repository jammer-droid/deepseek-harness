# DSH 업데이트 후 플러그인 호환성 대응

DSH 업데이트 뒤 Studio 또는 함께 사용하는 로컬 플러그인에 `incompatible with DSH` 경고가 뜨거나, 설치·로딩·기존 기능이 실패할 때 따른다. 대상은 **수정하지 않은 DSH에 설치하는 플러그인**이다. 변경 범위와 승인 기준은 [Studio 작업 지침](../../AGENTS.md), 독립 배포 조건은 [이슈 작업 절차](../design-workflow.md)를 따른다.

## 1. 대상과 작업 범위 확정

먼저 `git status --short`로 기존 변경을 확인하고 다음을 기록한다.

| 대상 | 확인할 내용 |
| --- | --- |
| 오류 | 경고 전문, 발생 시점, 설치 차단인지 실행 중 실패인지 |
| 런타임 | 실제 앱 버전, 실행 파일 경로와 그 파일의 `--version` 결과 |
| 설치 | 실제 DSH home·프로필, 플러그인 이름·버전·설치 경로·설치 소스 |
| 소스 | 해당 설치물을 만든 checkout·커밋·로컬 포크 및 lockfile |
| 권한 | 조사, 코드 수정, Desktop 설치·재시작 중 요청된 범위 |

PATH의 `dsh`와 Desktop에 포함된 런타임이 같은지 확인한다. 로컬 소스의 manifest와 **설치된 패키지의 manifest**를 각각 읽는다. 같은 버전 문자열이어도 다른 빌드일 수 있다. 함께 경고가 난 플러그인은 각각 조사하며, Studio 수정 권한을 제3자 플러그인 변경 권한으로 확대하지 않는다.

“확인해 봐”는 읽기 전용 조사다. 수정 요청에는 필요한 빌드·테스트·격리 설치 검증을 포함한다. Desktop 반영까지 요청받았다면 백업·설치·필요한 재시작·확인을 이어서 수행하고 이미 받은 승인을 다시 묻지 않는다. 진행 중인 작업 때문에 종료가 곤란하면 상태를 보존하고 재시작만 미완료로 보고한다. 공개 배포·푸시 등은 요청 범위를 별도로 판단한다.

**완료 기준:** 런타임·설치 패키지·수정할 소스가 연결되고, 수행할 범위가 특정됐다. 다른 작업의 미커밋 변경이 있으면 구현·빌드는 별도 worktree에서 수행한다.

## 2. 선언 차단과 실제 비호환 구분

1. 대상 DSH 버전의 공개 호환성 검사 규칙을 확인한다. 가능하면 설치된 manifest를 그 버전의 검사 함수에 넣어 파일 변경 없이 재현한다.
2. `engines.dsh`, DSH 관련 `peerDependencies`, 정확한 prerelease 범위를 확인한다. 어떤 필드가 판정을 결정하는지는 **대상 버전의 구현**을 근거로 삼는다.
3. 이전에 검증한 DSH 버전과 새 버전 사이에서 플러그인이 실제 사용하는 공개 API를 비교한다. import·exports뿐 아니라 이벤트 순서, 등록·해제, 서비스 scope, 설정 스키마, RPC, Client 외부 모듈, 저장·복원 계약도 변경 기능에 맞춰 확인한다.

| 판정 | 다음 행동 |
| --- | --- |
| 새 버전이 선언에 없고 사용 API의 변경을 찾지 못함 | 지원 선언을 갱신한 후보를 만들고 실제 설치 검증 |
| 사용하는 공개 API나 동작 계약이 변경됨 | 플러그인 내부에서 대응하고 해당 동작 회귀 검사 |
| 필요한 공개 API가 없거나 코어 수정이 필요함 | 지원 제약·대안을 보고하고 해당 경로의 구현 중단 |
| 선언은 통과하지만 로딩·실행이 실패함 | 최초 오류와 실제 호출 경로를 재현하여 원인 조사 |

호환성 경고는 실제 충돌·데이터 손실의 증거가 아니다. 반대로 소스 비교에서 차이를 찾지 못한 결과도 실행 호환성의 증거를 대신하지 않는다. `allow-version` 같은 예외 허용으로 검사 실패를 숨기거나, `*`·광범위한 범위로 미검증 미래 버전을 지원한다고 선언하지 않는다.

**완료 기준:** 플러그인별 차단 조건, 확인한 API 변경, 남은 실행 검증이 구분됐다.

## 3. 플러그인 범위에서 수정

- Studio 배포 manifest와 런타임 버전을 검사하는 개발·미리보기 스크립트를 함께 찾고 갱신한다. 기존 지원 버전 유지 여부는 코드 경로와 검증 근거로 결정한다.
- 실제 API 변경은 공개 확장점으로 흡수한다. DSH 소스는 읽기 전용 참고 자료이며 플러그인을 통과시키기 위해 본체를 수정하지 않는다.
- 로컬 포크는 원본 출처·라이선스를 보존하고 식별 가능한 로컬 버전을 부여한다. 개발 의존성을 갱신할 때 그 포크가 실제 사용하는 lockfile만 갱신한다. 다른 플러그인을 Studio 배포 번들에 섞지 않는다.
- 테스트 준비 코드가 바뀐 생성자·설정 스키마를 사용하는 경우 새 공개 계약에 맞춘다. 제품 결함과 테스트 준비물의 결함을 구분하고 실패를 무시하지 않는다.

**완료 기준:** 의도한 파일만 변경됐고 `git diff --check`가 통과한다. 선언만 바뀐 경우에도 다음 단계의 컴파일·실제 설치 결과로 지원 여부를 판단한다.

## 4. 빌드와 격리 설치 검증

현재 package scripts를 확인해 변경 기능 테스트·Studio 타입 검사·빌드를 실행한다. workspace 테스트 결과는 개발 중 회귀 근거로 기록한다. 검증 준비물 부족 때문에 루트 전체 빌드나 DSH 재빌드를 자동 실행하지 않는다.

이어 다음 순서로 배포물을 검증한다.

1. 새 출력 디렉터리에 정상 배포 tgz를 만든다. 같은 버전을 다시 패키징할 때도 새 파일 경로를 사용하여 이전 tarball 캐시 재사용을 피한다. 패키지 버전과 SHA256을 기록한다.
2. 새 절대 경로의 `DSH_HOME`과 전용 프로필·빈 포트를 정한다. 모든 테스트 런타임·설치 명령에 해당 home과 프로필을 명시한다. 사용자 인증 정보는 격리 환경에 복사하지 않는다.
3. 지정 버전의 **미수정 배포 런타임**에 tgz만 공식 플러그인 설치 명령으로 설치한다. workspace 소스 절대 경로를 로딩한 결과로 대체하지 않는다.
4. Loader·Host·Client 로딩과 변경에 관련된 RPC·UI·사용자 흐름을 확인한다. 여러 플러그인을 함께 배포하면 동시 로딩도 검사한다.
5. 역할 정책·세션 복원·수명이 바뀌었다면 실제 자식 생성·동일 자식의 프로세스 재시작 후 복원까지 검사한다. 필요한 상세 절차는 [역할 호환성 검증 가이드](../../scripts/agents/checks/dsh-role-compat.md)를 참고하되 버전·fixture·기대값을 현재 계약에 맞춰 확인한다.

진단 wrapper를 썼다면 정상 패키지를 별도로 설치해 확인한다. Desktop에는 진단 코드가 없는 검증된 정상 tgz를 사용한다. 실제 모델 호출이 필요한 검사는 호출 범위를 먼저 알리고, 로컬 테스트 어댑터 결과와 외부 모델 결과를 구분한다. 인증·유료 호출에 필요한 권한이 없으면 해당 항목을 미검증으로 남긴다.

**완료 기준:** 정확한 런타임과 tgz에서 설치·로딩·선택한 기능 검사가 통과했다. 실패·건너뜀·미검증 항목이 기록됐다. 설치 검증이 막혔다면 Desktop 배포 준비가 끝났다고 보고하지 않는다.

## 5. 승인된 Desktop 반영

1. 실제 Desktop home·프로필과 현재 설치 소스를 다시 확인한다. 교체 전 manifest·lockfile·관련 설정과 복원에 필요한 기존 tgz를 확보한다. 데이터 형식 변경이 있다면 해당 사용자 데이터도 백업한다. 백업·인증 정보는 Git에 넣지 않는다.
2. 앱을 정상 종료하고 종료 여부를 확인한다. 다른 DSH 프로필이나 무관한 프로세스를 일괄 종료하지 않는다.
3. 격리 검증에 사용한 정상 tgz를 공식 `dsh plugin --profile <대상> add <tgz>` 경로로 설치한다. 활성 bundle과 중복 플러그인 여부를 확인한다. 기존 인증 저장소는 보존한다.
4. 설치된 manifest·Host·Client 및 변경 기능 번들의 해시나 바이트를 tgz와 대조한다. 같은 버전 문자열만으로 새 빌드 반영을 판정하지 않는다.
5. 앱을 재실행하고 플러그인 활성 상태·실행 구성 요소·호환성 경고 제거·실제 화면을 확인한다. Studio는 기존 프리셋 표시를, Subscriptions는 기존 계정 상태 조회를 확인한다. 신규 로그인이나 기존 계정 삭제를 검증 수단으로 사용하지 않는다.

**완료 기준:** 설치된 파일과 실행 중인 앱에서 새 빌드를 확인했다. 설치만 성공하고 재시작하지 않았다면 “설치 완료, 실행 반영 미확인”으로 보고한다. 화면·상태 조회 성공과 실제 모델 응답 성공은 따로 기록한다.

## 6. 실패 시 복구와 완료 기록

격리 검증 실패는 사용자 Desktop에 반영하지 않고 원인을 고친다. Desktop 설치·재시작 후 문제가 생기면 새 오류를 보존하고, 백업을 기준으로 영향받은 패키지·활성 설정·필요한 데이터만 복원한다. 복구 과정에서도 다른 작업의 변경은 보존한다.

**이전 tgz가 새 DSH와 호환되는지 먼저 확인한다.** 이전 조합이 앱 업데이트로 이미 차단됐다면 그 tgz 재설치만으로는 복구되지 않는다. 현재 런타임에서 검증된 플러그인 또는 승인된 런타임·플러그인 조합으로 복구해야 한다. 앱 다운그레이드는 별도 시스템 변경으로 취급한다. 가능한 조합이 없으면 영향받은 플러그인 비활성화 등 대안을 사용자에게 제시한다. 예외 허용을 복구 성공으로 기록하지 않는다.

완료 보고와 `verification/` 기록에는 다음을 남긴다.

- 원인과 변경 범위, 런타임 버전·실행 경로, 플러그인 버전·tgz·해시
- 실제 검사 명령·결과와 실패·건너뜀·미검증 항목
- 미수정 런타임 독립 설치 결과와 Desktop 설치·재시작·UI 확인 결과
- 백업·복구 경로, 종료한 검증 프로세스, 보존할 산출물

검증 서버를 종료하고 필요한 산출물을 보존한 뒤 임시 작업 공간을 정리한다. 설치된 프로필이 참조하는 로컬 tgz 경로는 유지한다. 새 버전 검증 기록은 새 파일로 작성하고 과거 기록을 최신 결과로 덮어쓰지 않는다.
