# Studio 컴포넌트 기반 워크플로우 기획서

## 요약

Studio는 에이전트의 모든 행동을 절차로 지정하는 실행기가 아니라, 에이전트가 사용할 지침·도구·모델·실행 환경을 조립하는 편집 환경이다. 사용자는 구성을 이해하고 실행 결과를 살펴 개선한다. 이 문서는 합의된 제품 계획이며, 현재 구현 완료를 뜻하지 않는다. 구현 요구사항은 [명세서](workflow-specification.md), 현재 코드의 근거와 제약은 [구성 조사](workflow-composition-research.md)와 [실행 조사](workflow-runtime-research.md)에 둔다.

## 제품 원칙

1. 에이전트의 자율성을 기본으로 한다. 작업 분해, 도구 선택, 위임, 리뷰 활용, 실패 대응을 모든 경우의 수에 대한 규칙으로 만들지 않는다.
2. 컴포넌트는 능력과 환경을 제공한다. 권한 제한이나 사용자가 명시한 필수 호출처럼 필요한 제약과, 일반적인 작업 지침을 구분한다.
3. DSH의 기존 루프·서브에이전트·실행 제어를 재사용한다. Studio 전용 큐, 취소 체계, 복구 실행기를 첫 구현에 추가하지 않는다.
4. 기본 기능과 무엇이 달라지는지 설명한다. 모델이 받는 지침·도구·입력·결과의 변화와 한계를 설명하되 성능 향상을 보장하지 않는다.
5. 자유로운 조립과 명확한 적용 범위를 함께 제공한다. Host 전체의 변경을 특정 워크플로우에만 적용되는 설정처럼 표시하지 않는다.

## 구성 개념

| 개념 | 의미 |
| --- | --- |
| 컴포넌트 | 재사용 가능한 기능의 설정·입출력 정의. DSH 플러그인 하나와 반드시 일대일로 대응하지 않는다. |
| 엔티티 | 컴포넌트 조합과 연결·적용 대상을 보유하는 대상. 에이전트와 워크플로우가 주요 편집 대상이다. |
| 시스템 | 엔티티의 시스템 구성과 컴포넌트 조합을 읽어 로직을 수행하는 플러그인 구현. 핵심 코드는 Studio에서 편집하지 않는다. |
| 워크플로우 | 포함된 역할, 메인, 컴포넌트와 시스템을 묶은 사용자 구성. 사용자에게는 하나의 선택 가능한 DSH 프리셋으로 제공한다. |
| 역할과 인스턴스 | 역할은 설정이며 같은 역할로 여러 독립 에이전트 인스턴스를 생성할 수 있다. |
| 실행 | 메인 대화 세션 하나. 후속 메시지는 같은 실행에 속하고 하위 에이전트도 그 실행에 소속된다. |

시스템의 논리적 소속은 워크플로우이며 구현 코드는 재사용한다. 워크플로우마다 별도 프로세스나 서비스 인스턴스가 필요하다는 뜻은 아니다. 컴포넌트는 엔티티 종류를 감지하여 의미를 바꾸지 않으며, 시스템과 연결 구성이 적용 대상과 호출 방식을 결정한다.

## 사용자 경험

사용자는 완성된 개발 팀 템플릿으로 시작한다. 현재 DSH에서 선택 가능한 모델 목록에서 모델을 한 번 고르면 메인·구현자·리뷰어의 초기값으로 복사된다. 이후 역할별로 독립 수정하며 메인도 다른 에이전트와 같은 편집 대상이다.

기본 화면은 엔티티 목록과 컴포넌트 설정 패널이다. 지침·도구·모델 등의 컴포넌트를 추가하고 펼쳐 편집한다. 필요한 시스템이 없으면 추가·연결을 안내한다. 복잡한 노드 그래프 편집기는 초기 필수 범위가 아니다.

에이전트 정의와 이름 있는 컴포넌트 설정 템플릿은 워크플로우 밖에서도 저장·재사용한다. 가져오기 시 설정을 복사하며 원본과 복사본의 변경은 자동 전파되지 않는다. 실행 코드까지 복사하는 것은 아니다.

초안 저장은 프리셋을 바꾸지 않는다. 사용자가 적용하면 검증된 구성을 Studio 소유의 별도 사용자 프리셋으로 제공한다. 기존 DSH 프리셋은 덮어쓰지 않는다. 진행 중인 실행에는 변경을 소급 적용하지 않는 것이 목표이며, 재시작 이후 동일 구성 복원에는 현재 DSH와의 차이가 있다.

개발 템플릿은 메인이 명세를 확인하고 구현자·리뷰어를 활용하도록 지침과 도구를 제공한다. 구현 → 리뷰 → 재작업을 강제하는 승인 절차가 아니며, 메인이 직접 답하거나 필요한 작업만 위임할 수 있다.

## 첫 구현 범위

| 컴포넌트 | 제공할 설정 | 한계 |
| --- | --- | --- |
| 모델 | 역할별 모델·지원되는 추론 설정 | 현재 DSH 모델 목록 재사용, 임의 모델 목록 별도 관리 없음 |
| 지침 | 이름 있는 블록 추가·편집·제거·순서 | 기본 섹션 교체·제외는 실제 지원 지점만 노출 |
| 도구 | 기존 도구 묶음·개별 포함과 제외 | 제외는 실제 실행에서도 차단, 외부 연결·인증 관리는 제외 |
| 스폰·위임 | 대상 역할, Fork/새 컨텍스트, 추가 지침, 기존 자식 재사용 | DSH 지원 범위에서만 설정 제공 |
| 접근 권한 | 실제 실행 환경이 강제할 수 있는 역할별 설정 | 부모보다 넓은 자식 권한은 현재 지원 여부와 분리하여 표시 |
| 컨텍스트 | 윈도우 크기·자동 압축 시점 | 압축 로직은 DSH 기본 사용, 커스텀 요약 시스템은 제외 |

컴포넌트·시스템 등록 정보를 읽어 기본 설정 화면을 구성한다. 새 플러그인마다 Studio 본체의 조건 분기를 추가하지 않는다. 복잡한 기능은 전용 편집 UI를 제공할 수 있다. 의존성 누락이나 지원하지 않는 설정은 명확하게 표시하고 허위 적용 상태를 만들지 않는다.

첫 구현은 DSH 내부에서 실행하는 시스템만 제공한다. 역할별 독립 권한, 재시작 이후 과거 구성 고정 등 기존 기능으로 충족되지 않는 항목은 조용히 근사하지 않고 후속 또는 구현 전 결정 항목으로 분리한다.

## 후속 범위

- Jev 결정 컴포넌트: state와 typed questions를 입력하고 typed answers를 반환하는 범용 판단 기능. 모델·역할 선택에 국한하지 않는다.
- 시스템별 실행 방식: DSH 내부 / Studio 런타임 / 양쪽 지원. 지원되는 방식만 선택하며 한 워크플로우에서 여러 시스템과 혼합 실행을 허용한다.
- 모델 없는 구성 미리보기: 샘플 입력과 대체 응답으로 입력 구성·변환·연결을 확인한다. 부수 효과와 모델 성능 평가를 포함하지 않는다.
- 상세 실행 관찰: 우리가 제공하는 시스템의 실제 적용 기록과 가능한 입출력 전후 비교. 외부 플러그인 전체의 자동 추적을 약속하지 않는다.
- 원본 업데이트 가져오기: 복사본과 원본의 비교·병합은 별도 설계한다.
- 재시작 후 실행 당시 구성과 진행 상태의 복원: 현재 DSH가 보장하지 않는 부분의 저장·호환성 전략을 정한다.

## 구현 순서와 완료 기준

1. 구성 저장·등록: 엔티티, 컴포넌트, 시스템 참조와 독립 복사, 초안 저장을 구현한다. 등록 해제·누락 의존성·동시 편집을 검증한다.
2. 기본 개발 팀 편집: 여섯 컴포넌트를 DSH 지원 항목과 연결하고 현재 모델 목록을 사용한다. 메인도 같은 편집 경로를 사용한다.
3. 프리셋 적용: 새 프리셋 생성·갱신 경로와 Studio 소유권을 확정하고 적용 실패를 사용자에게 표시한다. 기존 일반 프리셋 편집과 구분한다.
4. 자율적 위임: 현재의 고정 역할·강제 리뷰 정책을 새 템플릿에 그대로 옮기지 않는다. DSH 하위 에이전트 기능으로 생성·후속 대화를 연결한다.
5. 제품 검증: 실제 Loader 구성 테스트, 모델에 보이는 입력 스냅샷, 저장·재시작 시나리오, UI 테스트로 지원 범위와 제약을 검증한다.

성공 기준은 사용자가 코드를 수정하지 않고 개발 팀을 구성하여 별도 프리셋으로 사용할 수 있고, 어떤 기능이 모델에 무엇을 제공하는지 이해할 수 있는 것이다. 모든 모델 행동을 통제하거나 결과 품질을 보장하는 것은 완료 기준이 아니다.

## 개발 메모

이 문서는 구현 승인이 아닌 기획 기준이다. 조사에서 드러난 지원 공백은 명세서의 결정 항목을 통해 해소한 뒤 해당 구현 단계를 시작한다.
