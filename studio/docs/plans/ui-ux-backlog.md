# Studio UI·UX 개선 백로그

## 목적과 기준

- 기준 구현: `feat/lean-agent`, `4f42345dd8` (역할 모델 런타임 검증).
- 대상: 수정하지 않은 Desktop DSH `0.2.0-rc.2`에 설치하는 Studio.
- 사용자는 프리셋·역할 기능과 모델 수정 후 실제 호출을 확인했다. 이는 모든 화면·접근성·세션 수명 동작의 검증을 의미하지 않는다.
- 이 문서는 개선 계획이다. 아래 항목은 별도 완료 증거가 없으면 **미착수**이며, 신규 기능 명세나 현재 지원 보장이 아니다.
- 범위: Studio 화면·문구·공개 API 연결. DSH 코어 수정, 저장 데이터 자동 치환, 별도 실행 엔진은 제외한다.

## 대표 사용자 흐름

1. 프리셋 목록에서 Master와 Optimized의 차이를 이해한다.
2. Optimized를 선택하거나 복사하고 도구·설정·역할을 편집한다.
3. 초안을 저장하고 기존 적용본과의 차이를 확인한다.
4. DSH에 적용하고 변경이 반영되는 세션 범위를 확인한다.
5. 역할 호출을 수행하고 결과 또는 복구 가능한 오류를 확인한다.

각 단계에서 선택 항목, 미저장 여부, 적용 상태, 다음 행동이 명확해야 한다.

## 우선순위와 증거 규칙

- P1: 상태 오해, 오류 은폐, 실제 실행 구성과의 불일치를 먼저 해결한다.
- P2: 편집·탐색 비용과 용어 이해도를 개선한다.
- P3: 추가 실행 도구 등 기능 확장을 검토한다.
- **관찰**은 이번 개발·사용 중 확인한 사실, **점검 필요**는 아직 재현하지 않은 위험, **제안**은 새 기능 후보다.
- 각 항목은 독립 변경으로 검증하고, 완료 시 커밋·런타임·검사·화면 증거와 남은 제한을 추가한다.

## 개선 항목

### UX-01 · P1 · 저장·적용·현재 세션 구분

- 관찰: 저장 파일을 외부 편집해도 마운트된 역할 설정은 즉시 갱신되지 않았다. 플러그인 업데이트는 앱 재시작을 요구했다.
- 문제: 저장, 적용, 실행 중인 설정과 설치 업데이트를 같은 동작으로 오해하기 쉽다.
- 기대: 초안/수정됨/적용됨, 마지막 적용 시각, 적용 후 필요한 행동을 구분한다. 플러그인 재시작 안내를 프리셋 저장 안내와 섞지 않는다.
- 수용: 저장만으로 실행 설정이 바뀌었다고 표시하지 않는다. 적용 실패 시 마지막 정상 적용본 유지 여부를 알려준다. 새 세션과 기존 세션의 반영 범위를 실제 검증한 뒤 문구를 확정한다.
- 선행: 기존 Agent가 보유한 프리셋 리비전 및 재적용 수명 확인. 자동 파일 감시는 기본 해결책이 아니다.

### UX-02 · P1 · 오류와 빈 상태 분리

- 관찰: Host API 404와 “저장된 프리셋이 없습니다”가 함께 표시된 사례가 있었다.
- 문제: 불러오기 실패를 데이터 없음 또는 소실로 오해한다.
- 기대: 로딩/조회 성공 0건/조회 실패/저장 중/적용 중/적용 실패를 상호 구분한다.
- 수용: 조회 실패에는 빈 상태·생성 유도를 보여주지 않는다. 재시도와 안전한 다음 행동을 제공한다. 재조회 실패가 편집 입력을 지우지 않는다. 중복 저장·적용을 방지한다.
- 검증: API 실패, 지연, 성공 0건, 성공 N건, 저장·적용 실패를 각각 주입한다.

### UX-03 · P1 · 역할 모델 상태와 복구 안내

- 관찰: 저장된 `deepseek-official` provider와 데스크톱의 `deepseek-account` 어댑터가 달라 `NO_ADAPTER`가 발생했다.
- 현재 해결: 런타임 목록 기반 선택, 적용·호출 전 provider/model/reasoning 검증, 목록 미확인 문구 보정. provider 자동 치환은 하지 않는다.
- 남은 점검: 로딩, 인증·목록 조회 실패, 미등록 provider, 모델 검증 실패를 사용자가 구분할 수 있는가.
- 기대: 모델 표시 이름과 실제 ID를 구분하고 문제 역할로 이동할 수 있다. 기존 선택값은 보존한다. 모델 변경 시 reasoning 초기화 이유를 안내한다.
- 수용: 조회 실패를 미등록으로 단정하지 않는다. 오류에 역할·수정 위치·저장 및 재적용 방법이 나타난다. 비밀값·인증 헤더를 노출하지 않는다. 다른 provider로 자동 대체하지 않는다.

### UX-04 · P1 · 선택 도구와 실제 적용 도구 일치

- 관찰: 실행 역할이 있으면 일반 위임 도구가 제외되고 `studio_role`이 추가되는 정책이 있다. 편집 목록과의 차이는 추가 검증이 필요하다.
- 기대: 직접 선택/자동 추가/정책상 제외를 구분하고 그 이유를 표시한다.
- 수용: 적용 전 표시한 실효 도구 목록과 해당 프리셋의 실제 도구 목록을 비교한다. 역할 추가·제거 시 차이가 갱신된다. 표시 보정을 위해 정책을 완화하지 않는다.

### UX-05 · P2 · 프리셋 탐색과 안전한 편집

- 점검 필요: Master 읽기 전용, Optimized 편집 가능·삭제 불가, 복사, 적용 해제의 차이가 명확한가.
- 기대: 버튼 동작과 비활성 사유가 명확하고 수정됨 표시의 비교 기준을 설명한다.
- 수용: 편집 후 이동·프리셋 전환 시 미저장 데이터 처리 규칙을 정의하고 검증한다. 복사본 변경이 원본에 영향을 주지 않는다. 적용 해제와 삭제를 구분한다.

### UX-06 · P2 · 도구·Config 탐색과 상속 표시

- 점검 필요: 많은 항목에서 선택값·변경값·기본값을 찾기 쉬운가.
- 제안: 선택 항목만 보기, 변경 항목만 보기, 이름·설명 검색, 검색 결과 수와 초기화.
- 수용: 기본값/상속/사용자 지정/명시적 빈 값·false·0을 구분한다. 초기화는 무엇을 복원하는지 설명한다. 미지원 스키마를 임의 JSON 입력으로 우회하지 않는다.

### UX-07 · P2 · 역할 용어와 실행 의미

- 점검 필요: `inherit`, `fresh`, `fork`, persona와 reasoning의 의미를 이해하는가.
- 기대: 표시 이름 옆 짧은 설명과 필요 시 상세 도움말을 제공한다. Fresh는 독립 지시, Fork는 완료된 부모 대화 상속이라는 차이를 설명한다.
- 수용: 부모 설정 상속과 모델 기본값을 구분한다. 역할 변경 후 저장·재적용 안내를 제공한다. 문구가 실제 공개 API 동작보다 강한 격리·권한 보장을 약속하지 않는다.

### UX-08 · P3 · 역할 호출 테스트 진입점

- 제안: 역할 설정 화면에서 작은 테스트를 실행하고 성공·실패를 확인한다.
- 선행 결정: 비용 안내, 실행 동의, 별도 테스트 세션 수명, 취소, 결과 조회·보존 정책. 공개 API로 가능한 범위 확인.
- 수용: 클릭 전 모델 호출 및 비용 발생 가능성을 알린다. 설정 저장·적용과 실행을 분리한다. 운영 대화에 테스트 메시지를 몰래 삽입하지 않는다. fork/fresh 검증은 부모에만 있는 표식을 이용하고 기밀 대화를 증거에 복사하지 않는다.

## 공통 품질 체크리스트

- [ ] 라이트·다크 모드에서 텍스트·상태·포커스 대비 확인
- [ ] 좁은 창과 긴 provider/model ID에서 가로 넘침·버튼 잘림 확인
- [ ] 키보드 탐색, 입력 라벨, 오류 알림, 포커스 복귀 확인
- [ ] ko/en/zh 문구와 저장·적용·적용 해제·초기화 동사 통일
- [ ] 늦은 응답·재연결이 최신 편집 상태를 덮어쓰지 않는지 확인
- [ ] UI 단위 테스트와 실제 설치 GUI 확인을 분리 기록

## 완료 기록 방식

각 UX-ID에 상태, 변경 커밋, 수용 조건 결과, 검증한 DSH 버전, 화면 조건, 미검증 항목을 추가한다. 스크린샷이나 실행 기록은 검증 문서에 두고 연결한다. 백로그 작성만으로 구현·배포·이슈 종료를 주장하지 않는다.
