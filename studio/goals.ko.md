# Harness Studio — 제품 목표

## 요약

이 포크의 주목적은 DSH Studio 플러그인 개발이다. Studio는 DSH의 하네스 구성을 관찰하고, 기능과 실행 정책을 조합하고, 프리셋으로 저장하여 반복 실험하는 개발 환경을 지향한다. 특정 커스텀 에이전트 하나나 플러그인 관리 화면만을 만드는 프로젝트가 아니다.

**하네스 관찰 → 구성 변경 → 프리셋 저장 → 실제 실행 → 결과 비교 → 개선**

이 문서는 Studio 작업의 제품 방향과 범위 기준이다. 목표 기능이 이미 구현되었다는 뜻은 아니다. 개발 절차와 설치 환경은 [개발 안내](development.ko.md)를 따른다.

## 해결할 문제

Standard / PTC / Minimal / Creator 같은 모드 이름만으로는 실제 도구, 문맥, 모델 설정, 실행 정책과 결과 차이를 파악하기 어렵다. 사용자는 기본 하네스를 이해하고, 필요한 판단이나 변환 기능을 추가하고, 변경 효과를 비교할 수 있어야 한다.

## 합의된 제품 목표

### Inspect — 구성과 실행 관찰

- 구성 보기: 선택한 프리셋의 드라이버, 모델 라우팅, 도구, 문맥, 훅, 실행 정책을 표시한다.
- 실행 보기: 특정 요청이 실제로 거친 단계, 판단 결과, 입력 변경, 도구 실행, 반복, 종료, 시간과 사용량을 표시한다.
- 설정상 활성화된 기능과 실제 호출된 기능을 구분한다. 관측할 수 없는 구간은 미관측으로 표시하며 실행된 것으로 추정하지 않는다.

### Compose — 기능과 실행 정책 조합

사용자는 모델 요청 전 모호성 판단, 독립 모델을 통한 입력 변환, 도구 실행 전 위험 판단, 도구 결과 검증, 종료 전 완료 검사 같은 기능을 추가하고 설정할 수 있어야 한다.

각 기능에는 호출 시점과 순서, 입력 문맥 범위, 모델과 출력 형식, 판단 결과에 따른 통과·질문·차단·재실행, 타임아웃과 오류 정책, 실행 횟수와 예산 제한이 필요하다. 화면에 블록을 표시하는 것만으로는 목표를 충족하지 않는다. 표시된 구성이 실제 실행에 적용되어야 한다.

### Preset — 저장과 재사용

사용자는 기존 프리셋을 복제하고 수정한 구성을 새 프리셋으로 저장한다. 새 프리셋으로 시작한 에이전트에는 해당 구성이 적용되어야 하며, 원본 프리셋과 다른 세션의 동작을 의도치 않게 바꾸면 안 된다.

### Experiment — 실행과 비교

사용자는 원본과 실험 프리셋을 실행하고 품질, 지연, 사용량·비용, 재시도·재작업을 비교하여 기능의 유지 여부를 결정한다. 실행 당시 구성과 판단 기록을 확인할 수 있어야 비교 결과를 해석할 수 있다.

## 필수 원칙과 성공 기준

현재 개발 범위는 이 포크의 Studio workspace이며 DSH 핵심 패키지는 수정하지 않는다. 공개 확장 지점으로 충족할 수 없는 요구사항은 제약과 대안을 제시하고 사용자와 범위를 결정한다. 조사 결과만으로 구현 방식을 자동 확정하지 않는다.

| 항목 | 성공 기준 |
|---|---|
| 구성 정확성 | 화면의 활성 구성과 실제 에이전트에 적용된 구성이 일치한다. |
| 실행 정확성 | 표시한 호출과 판단은 실제 실행 기록에 근거하며 선언·호출·미관측을 구분한다. |
| 격리 | 실험 프리셋의 구성·판단 상태·예산이 원본, 다른 세션과 자식 에이전트에 정의되지 않은 영향을 주지 않는다. |
| 반복 제한 | 종료 판단의 추가 실행에 독립적인 상한이 있어 무제한 반복을 막는다. |
| 오류와 취소 | 오류·잘못된 출력·타임아웃의 처리 정책이 명시되며, 취소 후 늦은 판단 응답이 추가 실행을 만들지 않는다. |
| 권한 | Studio 기능이 호스트의 도구 승인과 권한 검사를 우회하지 않는다. |
| 재현성과 복구 | 실행 당시 프리셋 버전과 유효 구성을 확인할 수 있고, 재개 시 구성 차이를 숨기지 않는다. |
| 관측 비용 | 보조 판단 호출도 사용량에 포함하고 수집하지 못한 항목은 명시한다. |

개발 에이전트의 모드와 실험 대상 하네스의 프리셋을 구분한다. 실행 정책 변경은 현재 작업 세션이 아닌 별도 개발 프로필에서 검증한다.

## 초기 범위에서 제외

- DSH 본체 전체 재작성 또는 기존 네 모드를 각각 새 드라이버로 재구현
- 임의 플러그인 코드를 완전한 시각 그래프로 자동 변환
- 첫 버전에서 모든 플러그인과 외부 에이전트의 호환성 보장
- 실행 중인 세션의 드라이버 즉시 교체
- 첫 단계부터 전체 벤치마크 실행

## 근거와 적용 범위

제품 방향은 HEL의 [원본 계획](</Users/home/playground/vibecoding/HarnessEngineeringLab/docs/dsh/harness-studio-plan.md>), 조사 근거는 [1차 조사](</Users/home/playground/vibecoding/HarnessEngineeringLab/docs/dsh/harness-studio-research.md>)에서 가져왔다. 두 링크는 작성 환경의 로컬 자료를 가리킨다. 이 문서는 해당 경로가 없는 환경에서도 목표와 미확정 범위를 이해할 수 있도록 필요한 내용을 담는다.

원본 조사는 2026-10-10에 설치된 DSH `0.2.0-rc.2`의 배포 코드와 읽기 전용 Inspect를 대상으로 했다. 당시 네 모드는 서로 다른 네 드라이버가 아니라 기본 Host 루프에 연결되는 프리셋 구성이었으며, 기본 AgentLoop를 유지하고 종료 판단 훅을 추가하는 첫 실험이 가능하다는 정적 조사 결론을 얻었다.

이 결론은 현재 포크의 API 호환성이나 동시 실행·취소·복구 검증을 보장하지 않는다. 구현 시 현재 checkout에서 확장 지점과 프리셋 수명을 다시 확인한다. 사이드바와 데모 타이머 같은 개발 기반을 제품 목표의 달성으로 간주하지 않는다.

## Dev Note — 구현 후보와 미확정 사항

이 절은 제안이며 승인된 구현 명세가 아니다. 아래 후보와 선택지는 사용자 결정과 현재 코드 검증을 거쳐 확정한다.

### 첫 구현 후보: 최소 연결 실험

1. Standard 구성을 읽기 전용으로 표시한다.
2. 한 세션의 실제 실행을 단계별로 표시한다.
3. Standard를 복제한 실험 프리셋을 만든다.
4. 종료 직전 판단 훅 하나를 추가한다.
5. 원본과 실험 프리셋의 동시 실행 및 격리를 확인한다.
6. 판단 결과, 추가 실행, 지연, 사용량을 비교한다.

첫 검증에는 결정적인 테스트용 판단기를 사용하고 실제 외부 판단 모델 연결은 분리하는 방안을 권장한다. 호스트 통합 문제와 모델 판단의 불확실성을 구분하기 위해서다. 전체 그래프 편집기와 대체 드라이버는 이 연결을 검증한 뒤 확장하는 후보이다.

### 구현 전 결정할 사항

- 기본 루프 확장과 드라이버 교체를 어디까지 지원할지
- 알려진 개입 지점만 편집할지, 자유로운 그래프 편집을 제공할지
- 임의 플러그인 구성의 해석 범위와 미지원 구성 표시 방법
- 프리셋의 버전·실행 스냅샷·세션 복구 정책
- 판단 실패 시 통과·중단 정책과 반복·예산 제한
- Goal 자동 지속 및 자식 에이전트와의 관계
- 기존 모드 선택 UI와의 연결 방식

### 후속 후보: 계약 기반 하네스

Studio를 기반으로 프로젝트 요구사항을 계약으로 확정하고, 독립 문맥의 모델로 입력을 변환하여 구조화된 위임과 결과 검증을 수행하는 하네스를 실험할 수 있다. 요구사항 ID, 원문 출처, 계약 버전, 사용자 결정과 모델 추론의 구분을 추적하는 방향이다. JSON 스키마 검증과 의미 보존 검증은 별개로 다룬다.

평가는 순정 자유형 위임, 구조화만 적용한 위임, 독립 변환 모델과 검증을 적용한 위임을 비교하는 후보이다. 의미 보존과 작업 성공률·토큰·비용·시간·재작업을 함께 평가하되 모델, 예산, 벤치마크와 버전을 고정해야 한다. 이는 첫 구현의 필수 범위가 아니다.
