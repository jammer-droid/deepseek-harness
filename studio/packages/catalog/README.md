# Studio 역할 카탈로그

이 패키지는 기본적으로 꺼진 실험이다. Studio > 실험의 역할 카탈로그 카드에서 활성화 상태를 읽고 명시적으로 변경한다. 활성화하면 대화 헤더의 `subagent-catalog` 셀만 우선순위 `-1`로 교체한다. 기본 DSH 자식 목록을 기준으로 Studio 생성 스냅샷을 결합하며, 역할 정보가 없는 자식도 남긴다. 자식 실행과 대화 사이드바는 DSH가 소유한다. 비활성화하면 기본 카탈로그 셀이 다시 선택된다.

## 역할 작성과 호출

워크플로 초안의 `mainRole`이 호출 가능한 역할이다. 초안마다 임의의 이름과 구성요소를 저장하고, 카탈로그에서 역할·저장된 리비전·작업·새 컨텍스트 또는 분기 컨텍스트를 선택한다. 분기는 완료된 부모 턴을 상속한다. 호출 시 리비전이 달라졌으면 실행 전에 거절한다. 플러그인을 켠 뒤 이미 열린 편집기는 새로고침하여 구성요소 목록을 다시 읽는다.

- `studio.instructions` v1: `text`를 순서대로 합쳐 자식 persona로 전달한다. 비어 있지 않은 persona는 부모 persona 접두사를 대체하며 권한 제한이 아니다. 모두 비어 있으면 부모 persona를 상속한다.
- `studio.model` v1: 필수 `provider`, `model`과 선택 `reasoningEffort`를 DSH 모델 옵션으로 전달한다. 한 역할에 하나만 허용한다. 없는 경우 DSH의 부모 설정 상속을 사용한다.
- `studio.tools` v1: `allow`, `deny`에 도구 이름을 한 줄에 하나씩 적는다. DSH의 도구 표시 및 실행 제한에 전달하므로 부모 권한을 확대하지 않는다. 두 필드가 비어 있으면 추가 제한을 적용하지 않는다. 한 역할에 하나만 허용한다.

지원하지 않는 구성요소 ID·버전과 잘못된 구성은 실행 전에 거절한다. 프롬프트 문자열이나 기존 implementer/reviewer 이름으로 역할을 추론하지 않는다.

## 모델 호출

실험을 켠 뒤 새 세션에서 번들에 포함된 `Studio Roles` 프리셋을 선택하면 `studio_role` 도구를 제공한다. 사용자 프리셋에는 `@local/dsh-studio-catalog/tool`을 명시적으로 넣을 수 있다. Host의 catalog 플러그인도 활성화되어 있어야 한다. `action: roles`로 역할 ID와 리비전을 확인한 뒤 `action: launch`에 `roleId`, `revision`, `task`, `context`를 전달한다. 결과는 기본 DSH 자식 알림으로 도착한다. 기존 Studio 관리 프리셋이나 기본 에이전트 도구는 자동 변경하지 않는다.

## 저장과 실패

Studio 전용 `studio_role_catalog` 도메인에 자식 ID, 부모 ID, 역할 이름과 ID, 리비전, instructions, model, tools, task, context를 실행 요청 전에 저장한다. 이후 초안 수정은 생성 스냅샷을 바꾸지 않는다. 이 데이터는 실행 상태나 권한의 증거가 아니며, DSH가 발견한 자식에만 표시한다. 기존 Session 로그 형식은 변경하지 않는다.

예약 저장 또는 DSH 수락에서 오류가 발생하면 자식 ID가 포함된 `admission-unknown`으로 보고하고 해당 서비스의 추가 호출을 막는다. 자식 생성 여부를 확인하기 전 재시도하지 않는다. 재활성화는 이전 호출의 롤백을 뜻하지 않는다. 플러그인 종료는 새로운 호출을 막고 진행 중인 수락을 기다리며 플러그인 소유 신호를 취소한다. 모델 호출의 취소 신호는 예약 전까지 확인하고, 이미 수락된 자식은 짧은 도구 또는 Remote 호출 수명과 분리한다.

Remote 응답만 유실된 경우에는 서버가 이미 자식을 수락했을 수 있다. 클라이언트는 현재 대화 헤더가 유지되는 동안 추가 호출을 막지만, 화면 이동이나 새로고침을 넘어선 중복 방지 키는 제공하지 않는다. 목록과 자식 대화를 확인한 뒤 사용자가 다음 작업을 결정해야 한다.

## 검증 범위

구성 해석과 UI 모델의 단위 테스트는 실행 없이 저장값·리비전·지원 구성요소를 검증한다. 실제 프로필 설치, 제공자 모델 호출, 실행 중인 GUI의 밝은/어두운/좁은 화면 검증은 별도 승인과 환경이 필요하다.
